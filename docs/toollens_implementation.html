1. Overview

All 464 ToolLens tools across 19 categories have been generated as executable Python classes with deterministic return values, input validation, unit tests, and sequential integration tests. The implementation is driven by deepseek-v4-flash-free on the opencode zen endpoint, with retry logic and validation.

3. Generation Process

Each domain was generated through a 5-step LLM pipeline:

  1. Class code generation — LLM produces a complete Python class with METHOD_NAME_MAP, __init__, and all tool methods
  2. Input schema generation — Pydantic models for parameter validation
  3. Initial config generation — Default state for the domain class (step frequently fails for the free model; uses defaults)
  4. Unit test generation — Normal + edge-case tests per method
  5. Sequential test generation — Multi-call integration tests

Each step validates syntactic correctness and optionally runs pytest. Failed steps retry up to 2 times with the error message fed back as context.

3.1 Model: deepseek-v4-flash-free

The LLM provider is https://opencode.ai/zen/v1 using the free-tier model. Average response times:

  • Class generation (30-50 tools): 30-50s
  • Schema generation: 10-20s
  • Initial config: 25-35s (frequently returns empty responses)
  • Unit tests: 25-50s
  • Sequential tests: 20-30s

Total generation time for all 19 domains: ~45 minutes.

4. Key Design Decisions

4.1 METHOD_NAME_MAP

ToolLens api_name strings often contain characters illegal in Python identifiers (slashes, dots, apostrophes, spaces). Each class exposes a METHOD_NAME_MAP class attribute mapping the original api_name to the sanitized method name: 

METHOD_NAME_MAP = {
    '/v1/covid19': 'v1_covid19',
    "Today's International Current Affairs": 'Today_s_International_Current_Affairs',
    'auto-complete': 'auto_complete',
}

The __init__.py registry introspects each class to build TOOLLENS_API_NAME_TO_CLASS_KEY (api_name → class_key), used by ToolManager.register_tool_implementations().

4.2 Config Storage (no setattr)

Initial configs are stored in self._config_data dict rather than via setattr(self, key, value), preventing config keys from shadowing method names. The generator prompt was updated to instruct the LLM to use this pattern.

4.3 Error Handling

Methods never raise exceptions. Invalid inputs return error info in response dicts: 

{'error': 'Count must be between 2 and 20', 'words': []}

4.4 State Management

Domains with mutable state (e.g., CRUD operations) maintain collections in memory. Read-only domains (e.g., external API proxies) initialize minimal state like a call counter or cache.

5. ToolManager Integration

The ToolManager class was refactored to remove BFCL/ToolLens-specific code paths. Usage: 

from tools.toollens import get_toollens_api_name_map, create_toollens_tool_instances

tm = ToolManager(llm=llm, tool_pool_path='toollens_tools_enhanced.jsonl')
tm.register_tool_implementations(
    api_name_map=get_toollens_api_name_map(),
    instances=create_toollens_tool_instances(),
)
# invoke_tool now dispatches to ToolLens Python implementations
result = tm.invoke_tool('/v1/covid19', {'country': 'USA'})

Tools without Python implementations fall back to LLM-based simulation.

7. Known Issues

  • Sports tool count discrepancy — 35 tools in dataset, 26 methods generated. The LLM merged several competition/standing endpoints.
  • Initial config generation — The free model frequently returns empty responses for this step (~70% failure rate). Classes use default state when config generation fails.
  • Generated test assertion fragility — Some tests assert specific keys from the LLM-generated output (e.g., education test expects 'id' in result when the actual output uses 'question').
  • Sports List method conflict — A method named List shadowed typing.List. Renamed to ListTools.
